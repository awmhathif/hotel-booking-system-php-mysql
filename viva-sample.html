Questions and answers

About the project

Tell me about your project.

It's a web-based booking system for a small hotel. Guests search for free rooms by date and send booking requests. The admin confirms or rejects them, gives each booking a real room, checks guests in and out, records payments, prints invoices, manages room types and rooms, and replies to contact messages. It's built with PHP, MySQL, HTML, CSS and a little JavaScript on XAMPP.

What problem does it solve?

With a paper diary, rooms get double booked, guests can only book in office hours, and staff can't easily see who arrives today or who still owes money. The system checks free rooms for the dates automatically, takes requests any time, and shows the admin the waiting requests, today's arrivals and the balance of every booking.

Technology and architecture

Why PHP and MySQL, and why no framework?

They run on almost every web host and come together in XAMPP. I used plain PHP so I could understand and explain every line. A framework like Laravel would do sessions, CSRF and queries for me, but then I couldn't show how they work.

Explain the architecture.

Three tiers: the browser (HTML, CSS, a little JavaScript), the web server (Apache running PHP), and the database (MySQL). The browser requests a page, PHP runs, asks MySQL for data with prepared queries, builds the HTML and sends it back. The browser never talks to the database directly.

Database

Explain your tables and relationships.

Six tables. room_types is what guests book ("Lake View Double", with price and photo). rooms are the real numbered rooms, each pointing to a type. users holds guests and the admin. bookings points to users, room_types and, once confirmed, rooms. payments points to bookings. messages stands alone, because visitors can send one without an account.

Why are room types and rooms separate tables?

Guests choose a kind of room, not a room number, and the hotel has several rooms of each kind. The price, photo and description belong to the type, so they're stored once. The admin picks the real room when confirming. This is normalisation: each fact is stored in one place.

The booking logic

How do you prevent overbooking?

rooms_left() counts the rooms of the type, then the bookings of that type that clash with the dates and still need a room (waiting, confirmed or checked in). Rooms left = rooms − clashing bookings. The booking is refused when that is less than 1. Show: includes/functions.php, rooms_left().

How do you know two stays clash?

Two stays clash when one starts before the other ends: check_in < new check_out AND check_out > new check_in. Using < and > (not <=) means a guest can check in on the day another checks out, which is how hotels work.

Security

How do you prevent SQL injection?

Every query with user input is a prepared statement: $conn->execute_query($sql, [values]) with ? placeholders. The SQL and the values reach MySQL separately, so input can never change the query. Show: any query, for example login.php.

How do you prevent XSS?

Every value from users or the database is printed through my e() function, which uses htmlspecialchars. Typed HTML or script shows as text instead of running. Show: includes/functions.php, then any page.
